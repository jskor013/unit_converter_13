## 1. 작업 목적

UnitConverter C++ 프로젝트의 REFACTOR 단계에서 Dual-Track UI + Logic 분리를 진행했다. 새 기능 추가 없이 기존 외부 계약인 `unit:value` 입력, 변환 출력 형식, `std::invalid_argument` 기반 Boundary 예외 동작을 유지하면서, Boundary 책임과 Domain 변환 책임을 분리하는 것이 목적이다.

이번 백업은 다음 원칙을 따른다.

- `tests/unit_converter_contract_tests.cpp`는 사용자 지시에 따라 스켈레톤 RED 테스트로 제외한다.
- `build/` 산출물은 커밋하지 않는다.
- 접근 가능한 parent 대화 원문은 `/prompt`에 JSONL 원문으로 보존한다.
- README와 PRD의 기본 단위 변환, 출력 계약, Boundary/Domain 분리, 회귀 보호 규칙과 연결한다.

## 2. 변경 파일

구현 및 빌드 변경:

- `CMakeLists.txt`
  - `converter_core` 라이브러리 타깃을 추가하고 `UnitConverter`, `test_converter`가 동일한 변환 코어를 링크하도록 변경했다.
- `Converter.h`
  - 테스트와 앱이 공유하는 공개 변환 API와 `ConversionResult` 선언을 추출했다.
- `ConverterInternal.h`
  - 앱/Boundary가 사용할 내부 단위 검증 함수 선언을 분리했다.
- `Converter.cpp`
  - `ConversionRule` 기반 기본 단위 규칙 테이블을 도입했다.
  - 기존 단위 조합별 `if` 체인을 meter hub 변환 공식으로 단일화했다.
  - `RegisteredUnit` 구조체로 동적 등록 상태를 명시했다.
  - `convertAll()`이 기본 규칙 테이블을 순회하도록 중복 대상 단위 목록을 제거했다.
- `ConverterBoundary.cpp`
  - `convertInput()`의 입력 파싱, 숫자 검증, 음수 검증, 출력 포맷 생성을 Boundary Track으로 분리했다.
  - Boundary 예외 메시지를 상수화했다.
- `UnitConverter.cpp`
  - 앱 실행 경로가 자체 변환 분기와 매직 넘버 대신 `converter_core`의 `isKnownUnit()`과 `convertAll()`을 재사용하도록 변경했다.
- `tests/test_converter.cpp`
  - 수동 함수 선언 복제를 제거하고 `Converter.h`를 포함하도록 변경했다.

## 3. 요구사항 연결

- `README.md`
  - `meter`, `feet`, `yard` 기본 비율과 출력 포맷 `<source_amount> <source_unit> = <converted_amount> <target_unit>` 계약을 유지했다.
  - 새 단위 추가 시 기존 변환 분기 수정을 줄이는 OCP/SRP 학습 목표와 연결된다.
- `docs/PRD.md`
  - §3.2 입력 `<unit>:<amount>` 계약, 기본 단위 변환, 원 입력 보존 요구사항과 연결된다.
  - §4.2 Boundary는 파싱/출력, Entity는 단위 정의와 변환 규칙을 담당한다는 아키텍처 원칙과 연결된다.
  - §5.1 `1 meter = 3.28084 feet`, `1 meter = 1.09361 yard` 기준 비율을 유지했다.
  - §7.2 회귀 보호 규칙에 따라 스켈레톤 계약 테스트를 제외한 보호 테스트를 리팩터링 전후 실행했다.

## 5. 미완료 항목 및 다음 단계

- `tests/unit_converter_contract_tests.cpp`의 RED 스켈레톤을 실제 계약 테스트로 전환해야 전체 CTest를 GREEN 기준으로 사용할 수 있다.
- `UnitConverter.cpp`는 변환 로직 재사용까지 완료했지만, 콘솔 입력 파싱과 오류 출력은 여전히 앱 `main()`에 남아 있다. 다음 REFACTOR에서는 앱 Boundary도 `ConverterBoundary.cpp`의 파싱/포맷 흐름으로 더 좁힐 수 있다.
- 동적 단위 등록 상태는 `RegisteredUnit` 구조체로 명확해졌지만 여전히 단일 등록 단위만 보관한다. 다중 단위 레지스트리는 별도 기능/요구사항 승인 후 진행해야 한다.
- IDE clang 진단의 Catch2 include 경로 문제는 빌드 실패가 아니지만, 개발환경 진단 정리를 원하면 CMake compile commands 또는 clangd include 설정을 별도 점검할 수 있다.
